## Implemented domain, baseline, and protection behavior

A protected target is a normalized existing regular file or directory with a case-folded key and ACTIVE/DISABLED status. A trusted baseline is the target state captured at creation; code has no rebaseline/update function. A baseline file stores absolute/relative path, SHA-256 content state, filesystem identity, mtime nanoseconds, and size. Identity is formatted `st_dev:st_ino`; SHA-256 is of entire file bytes; only mtime (not size independently) is used for ordinary metadata-only classification.

Scanning rejects target symlinks/junctions and directory contents containing a symlink. A directory is recursive and files are ordered by sorted paths. Reconciliation compares current files against immutable baseline data. It first identifies by path but replaces that choice with matching filesystem identity if present; it detects renamed/moved files by changed relative name/parent, content modification by hash, and metadata change when mtime differs while neither rename/move nor hash difference applies. Missing baseline identity/path yields `DELETED`, except multiple SHA-identical current candidates yields the explicit low-confidence ambiguous result. A new current file not matched by a baseline result is `CREATED`. A baseline-path file with a different identity yields delete/recreate with `IDENTICAL` or `DIFFERENT` content. Compound move/rename/content results are supported. Size is captured but not independently compared. Move/rename detection is baseline-relative rather than chronological.

`create_protection` first inspects/scans the target, returns without database work when `confirmed` is false, then takes a fresh baseline before opening the database. The inserts for target, one baseline, and all baseline files occur under `with connection`; a duplicate ACTIVE normalized path raises `ProtectionError` and rolls back. An existing DISABLED protection does not block creating a new ACTIVE target because the unique index is partial. `enable_protection`/`disable_protection` change only status and preserve baseline/findings/evidence. The source has no CHECK constraint enforcing values, but the protection API accepts only the two named states.

## Watcher and monitoring implementation

The watchdog adapter uses `Observer`, schedules recursively, and converts callbacks to `CREATED`, `MODIFIED`, `DELETED`, or `MOVED`. It does not filter `event.is_directory`, does not debounce, and does not itself persist except through its supplied sink. `MOVED` preserves watchdog `src_path`/`dest_path`; `CREATED`, `MODIFIED`, and `DELETED` use `src_path`. Shutdown stops and joins observer.

`MonitoringCoordinator.start()` loads ACTIVE targets and baseline files from SQLite, schedules one recursive watcher per target; FILE targets watch their immutable target's parent directory, DIRECTORY targets watch their directory. Missing directories are skipped. Missing FILE paths are rediscovered only inside their original parent scope: it first tries persisted evidence `new_path`/`path` newest-first, then recursively scans that parent; a candidate is adopted only if its current identity matches a baseline identity. This runtime path does not update stored target/baseline data.

For each admitted event, `_on_event` captures a callback-time snapshot of destination/path (identity, hash, size, mtime; all null if unavailable/deleted/symlink), persists the raw normalized event into target-scoped `evidence_observations` in a transaction, then resets a per-target daemon timer. The default debounce is 0.15 seconds; only the timer/reconciliation is coalesced, not the raw observations. A persistence error is saved in `last_persistence_error`, sent to `error_sink`, and does not schedule reconciliation.

Directory targets admit events having any event path beneath their protected directory. A FILE target admits a sample whose identity matches baseline, a deletion at a previously tracked path, or an event at its baseline path; it rejects unrelated files in the watched parent. Tracked runtime paths change only after `MOVED` or inferred move.

`INFERRED_MOVED` is not a watchdog callback. It is generated only for a FILE-target raw `CREATED` event whose sampled current identity matches the baseline and when exactly one previously tracked path other than the new path no longer exists. Its old path is that one missing tracked path; its new/path are the created event path. It is persisted in addition to the raw observation with the same snapshot. It cannot be emitted for identity mismatch, non-FILE targets, non-created events, zero/multiple missing paths, or unrelated creates. Explicit `MOVED` remains raw `MOVED`; no conversion confuses the two.

After debounce, reconciliation runs against the directory target or a FILE target's original parent. FILE findings are retained when either their immutable baseline record or their current record concerns the immutable original target path, which preserves moved-file findings because the baseline record remains present. Non-`UNCHANGED` findings get a JSON baseline/current signature; only signatures absent from in-memory `_last_signatures` are inserted. In one transaction it inserts new findings then links every pending and previously unlinked observation to every persisted finding matching current signatures. On any database failure, it records/reports error and does not advance signatures or invoke finding sink. On commit it advances signatures and invokes sink for newly stored findings. Signatures/timers/tracked paths are in-memory; durable evidence and findings survive restart but signature state does not.

## History / interpretation

`target_timeline` is deterministic by SQLite `observation_id`, explicitly not `observed_at`. `interpret_finding` decodes baseline/current snapshots from `security_findings.signature`, so `previous_path` remains baseline-relative and is not treated as a chronological predecessor. With both records it can say current path differs, current content matches/differs, and modification time differs. It says historical evidence indicates content changed then returned to baseline only when caller-provided preceding findings contain the same baseline path and a non-baseline current hash. With no such preceding finding, a matching hash is only described as matching the trusted baseline. Ambiguous identical content produces its identity-confidence statement. Delete/recreate has no specialized narrative beyond what those conditions support. Timeline interpretation grouping/UI/CLI is not implemented.

## Security invariants and design boundaries

Implemented and verified: baseline records are not updated by reconciliation, monitoring requires ACTIVE targets, duplicate ACTIVE normalized paths are rejected, symlink/junction targets and discovered directory symlinks are rejected during baseline scan, identity supports continuity, SHA-256 and mtime have distinct comparison roles, target-scoped observations and finding links are durable after commit, and monitored persistence failure is visible/not treated as a successful scheduled reconciliation. SQLite foreign keys are enabled by `connect()`; caller-created raw `sqlite3.connect()` connections do not receive that setting automatically.

Partially implemented: evidence is durable and deterministic, but raw unscoped `filesystem_events` remains separate; finding/evidence relation is a batch association rather than proof each callback caused a specific finding.
